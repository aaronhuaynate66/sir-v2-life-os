# Auditoría SIR V2 — 2026-07-16

> Auditoría de cobertura end-to-end del sistema en producción. Ejecutada con agentes en paralelo + verificación del parent. Todo con evidencia real (no "health-check de fantasía").

## Metodología

Auditoría **de cobertura basada en riesgo** (estilo ISTQB smoke/sanity + exploratory charters):

1. **Inventariar** toda superficie del sistema (páginas, rutas API, bots, crons, integraciones, pipelines de datos) desde el código — no desde la memoria/docs.
2. **Por cada superficie**, definir un test concreto + resultado esperado.
3. **Ejecutar con evidencia real**: harness de sesión (login del test user `admin@cusmato.app` + cookie `@supabase/ssr` inyectada, contra PROD), webhooks sintéticos con el secret real (bots), y queries service-role a la DB (pipelines de datos, sobre el user real de Aaron).
4. **Registrar** PASS / FAIL / BLOCKED con la evidencia.
5. **Documentar** (este archivo) + separar hallazgos de humo.

Orquestación: 3 agentes en paralelo (superficie funcional · integraciones/bots/crons · pipelines de datos) + el parent probando los bots E2E y el pipeline dev.

Se confirmará el switch en cuanto se USE una ruta migrada (briefing, síntesis, decisión, etc.). *Acción: ninguna urgente; observar `ai_usage` tras uso real.*
2. **`learnings` vacía (Fase 3d).** La feature (tabla + `/api/learnings` + recall en el brief) existe y responde, pero nunca generó/guardó un learning. *Acción: verificar qué dispara la generación de learnings y si está cableada a correr.*
3. **`relationships` = 0 filas.** Vacía por diseño actual (la app usa people/observations). Consecuencia: el eje "estado de relación" del relationalScore no tiene data propia. *Acción: ninguna salvo que se quiera reactivar ese eje.*

## Resoluciones y seguimiento (2026-07-16, post-auditoría)

- 🐞 **BUG encontrado por Aaron — atribución cruzada (RESUELTO).** La ficha de Diana (novia = "Diana Carolina Díaz Sánchez") mostraba como "última interacción" una conversación de **"Carolina Insider One"** (otro contacto). Causa: `namesLooselyMatch` cruzaba por **un solo token compartido** ("carolina"). **Fix `#786`** (exige contención textual o ≥2 tokens; +tests). **Data limpiada + verificada**: 2 observaciones des-atribuidas de Diana + 35 chat_messages intrusos borrados; su historial real (71.852) intacto. Bonus: el fix también resuelve que su chat real "Diana Carolina ❣️" (antes ambiguo entre las 2 Dianas → no se atribuía) ahora se atribuya bien.
- 🐞 **Hallazgo 1 (ai_usage/OpenRouter) — BUG encontrado y RESUELTO.** Al ejercitar una ruta migrada en prod (`objetivos/suggest`, `tier:balanced`, `maxDuration=30`) → `FUNCTION_INVOCATION_TIMEOUT`. Causa raíz: el router mandaba **balanced** al más barato = OpenRouter **`qwen-2.5-72b`**, que tarda **>30s** en salida JSON estructurada → feature rota. (Solo `capable`/visión preferían Anthropic.) **Fix:** `balanced` ahora también prioriza **Anthropic Sonnet** (confiable); `cheap` (extracción simple, alto volumen) se queda en OpenRouter `llama-3.3-70b` (rápido, validado 1.3s) → **ahí vive el ahorro**. +3 tests del router. La telemetría `ai_usage` crecerá con uso real: verás `openrouter:...` en rutas cheap y `anthropic` en balanced/capable. **Follow-up IMPLEMENTADO (#788):** el router ahora prioriza para `balanced` el proveedor DIRECTO más barato (DeepSeek si su key está → barato **y** fiable con JSON) y **degrada OpenRouter a último recurso** (su modelo qwen es el que timea). Con `DEEPSEEK_API_KEY` en Vercel, `balanced` (y el `cheap` de texto) van a DeepSeek → **se recupera el ahorro** sin el riesgo de timeout; sin la key, `balanced` sigue en Anthropic. Nota: el grueso del volumen "cheap" es **visión** (capturas de salud) que SIEMPRE va a Anthropic (único multimodal), así que el ahorro real de OpenRouter/DeepSeek es sobre las rutas de texto.
- **Hallazgo 2 (learnings) — working as built.** No es bug: los learnings son 100% manuales (panel en `/yo` → `POST /api/learnings`, `source:'manual'`); no hay generación automática. El label "Fase 3d — memoria que aprende" es optimista (es notas durables + recall, ya cableado al brief/rehearse). Auto-derivación por IA = feature net-new si se quiere.
- **Hallazgo 3 (relationships=0) — by design.** La app usa people/observations; la tabla `relationships` no se puebla. Sin acción.
- **Hallazgo 4 (push VAPID) — pendiente decisión.** Push off (`configured:false`). Habilitar requiere setear `NEXT_PUBLIC_VAPID_*` en Vercel (cambio NEXT_PUBLIC_* → requiere confirmación de Aaron) y que efectivamente se quieran push.
